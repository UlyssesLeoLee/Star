# SRS-AUTOMATION-SCHEDULE-API-001 — Run-scoped Schedule Rule Management API

> Status: 🟡 Rule API, v2 multi-cluster contracts, isolated Infrastructure-owner schema/grants, Inbox receive, and tenant-scoped owner admission transaction are verified; trusted resolver, cross-tenant allocator, target DB identity/provisioning, owner consumer/outbox delivery, worker, provider evidence producer, and production execution remain open and fail-closed.
> Version: 0.22 | Date: 2026-10-07
> Parent: `docs/requirements.md` §50 and `docs/specs/domain-automation-spec.md` Schedule contract.

## 1. Purpose and boundary
Implementation acceptance supplement: ClusterPlacementPolicyV1 (shared_pool, run_dedicated, pinned_cluster) is pinned in the v2 binding and digest. The current test phase is limited to two registered Multipass instances total, including stopped/recoverable entries; the bootstrap launcher uses a host-local exclusive lock around full-inventory check plus launch, then refuses a third instance or an unparseable inventory without auto-purge. All live test launches must use the guarded path; Rust contract tests remain VM-free.


The API lets an authorized Project member manage recurring Automation rules for one Engineering Run. Every rule targets a current Run-owned Worktree and Task Card and pins the current execution Profile and effective HookSet. Rules are versioned Master data. This API does not start a Run or materialize/dispatch occurrences; those capabilities remain fail-closed until later Phase 9F gates connect the worker, resource reservations, final authorization, Run events, and BI.

## 3. Verification status

The Rust 1.98.1 bounded Schedule runner completed the previously recorded focused `rustfmt`, domain tests, API/adapter all-targets checks, targeted Clippy, and PostgreSQL integration harness compile. The new `domain-infrastructure` contract runner separately passed rustfmt, `cargo check --all-targets`, targeted Clippy, and all 8 crate tests. The pure schedule role-policy helper matrix test `task_execution_rules_do_not_grant_agent_role_schedule_authority` passed 1/1; it is separate from SQL evidence. Through production `build_group_router`, all four unauthenticated method/path cases return 401 with `Cache-Control: private, no-store` and `Vary: Authorization`; signed tokens with the wrong read/write scope return 403 before database access; a valid write-scope POST larger than 16 KiB returns 413. A lazy pool confirms these rejection paths do not reach PostgreSQL. The bounded Docker runner used disposable PostgreSQL 18.6, applied the 9F2/9F4A/9F4B/9F4C-A/9F4C-C migration chain twice, verified all eight Schedule tables use FORCE RLS, validated occurrence-to-Run/Outbox constraints and non-superuser tenant isolation, and passed all five ignored adapter PostgreSQL cases. The canonical Project/Branch/Engineering Run ACL fixture passed with a runtime role that has SELECT but no UPDATE privilege on directory ACL tables. Dual-connection race cases for Project, Branch, and Run revoke each observed the revocation block on the shared advisory lock while the authorization transaction was open; after it committed, revocation completed and subsequent authorization failed closed. These are implementation-slice checks only. Full route-to-database rollback, target currentness/revocation, concurrent CAS/replay, page boundaries, target database deployment, and production runtime-role grants remain open. No worker or Run admission service is enabled and Schedule execution remains fail-closed.

The 9F4D-3B1 runner passed 14/14 disposable PostgreSQL 18.6 gates, including repeat application of the grant migration and the full W/T privilege matrix. This is schema/grant-contract evidence only: target DB deployment, production login membership and SET LOCAL ROLE activation, owner stores/consumer, and Schedule execution remain open. The test gate used no Multipass instance; the current test-phase cap remains two registered instances total.

9F4D-3C1 verification: the focused Rust runner passed format, check, Clippy and tests for domain-infrastructure plus infrastructure. The disposable PostgreSQL 18.6 runner passed schema/grants assertions and the ignored SQLx Inbox receive case.

9F4D-3C2 verification: Rust formatting/check and the disposable PostgreSQL 18.6 owner integration suite exercise atomic Host+cluster reservation, same-resource concurrency, terminal replay/rejection and expired-hold capacity reuse. This does not prove a production consumer, trusted resolver/profile snapshot source, cross-tenant allocation, target DB migration/login activation, provider/Manager, worker, or VM. No Multipass instance is started; the test-phase cap stays at two registered entries because of disk capacity.
