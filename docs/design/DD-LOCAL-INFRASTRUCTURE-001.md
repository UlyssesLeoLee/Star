## §0 目的与边界

为渡口增加 provider-neutral 的 Rust Host Infrastructure Manager。**Multipass 是本地/CI Linux VM 的首选管理 provider，K3s 运行在由它管理的 Linux guest 中**；这是后续实现基线，不再是并列候选。Podman machine、Linux Incus、macOS/Linux Lima 按实际 capability 作为替换/备用 provider；用户自有或远端 Linux K3s 是独立集群路径，生产环境不依赖 Multipass。K3s 始终在 Linux host/guest/node 运行，不在 Windows 原生运行。Multipass 上游将产品定位为开发、测试与本地 VM 工具；拥有 Multipass daemon 权限可控制实例及高权限 host mount（[官方安全说明](https://canonical.com/multipass/docs/latest/explanation/about-security/)、[mount 安全说明](https://canonical.com/multipass/docs/stable/explanation/mount/)），因此 adapter 不能成为不可信 Agent 边界。Runtime sandbox 与 Hook 单独验收。K3d 仅复用已有容器引擎做开发/测试；Cloud Hypervisor 保留为 Linux 后续 PoC。已有宿主级实跑见 [`PHASE-MULTIPASS-K3S-GITOPS-REPORT.md`](../reports/PHASE-MULTIPASS-K3S-GITOPS-REPORT.md)：Windows 11 Home + Multipass 1.17.0-rc1/HCS 创建 Ubuntu 24.04.5 guest，运行 K3s v1.36.5+k3s1，并将 cert-manager、Argo CD、Argo Rollouts、Kargo 共 19 个 Pod 验证为 Running。该证据关闭了单机开发环境的宿主/K3s/GitOps PoC，不代表 Star 产品已实现通用 Rust provider adapter、Run namespace/授权绑定、Worktree bridge、不可信 Agent sandbox、跨 OS driver support 或目标 RSS；这些仍按本 DD 的 AC-INFRA-002 与阶段门独立验收。

Infrastructure Environment 是 Host/Project 可绑定的计算环境，不成为 Project → Branch → Run → Worktree 主树的新层级。Run 固定 environment/profile/version/digest、namespace 和预算；WorktreeFocus 提供服务端验证的 checkout/workspace 映射。配置放 Advanced Settings 的 Infrastructure 内容 tab，Run 只展示授权后的有效环境、状态与资源，深链回配置。

本项目的本地/CI K3s 运行基线不依赖 Docker Desktop；Multipass guest provisioning、K3s lifecycle/readiness 和 Run placement 必须可独立工作。Docker/container-engine adapter 如被选为其他 runner capability，需单独 opt-in 与 capability probe。

Multipass 的 CLI 支持机器可读 JSON inventory（[官方 `list` 文档](https://canonical.com/multipass/docs/stable-docs/reference/command-line-interface/list/)），并支持基于 cloud-init 初始化 VM（[官方 cloud-init 指南](https://canonical.com/multipass/docs/stable/how-to-guides/manage-instances/launch-customized-instances-with-multipass-and-cloud-init/)）。Manager 只解析有大小/时间上限的 JSON，cloud-init 与引用资源必须本地固定版本/digest；不把任意 URL、shell、用户输入参数透传为 privileged operation。

## §2 共享与隔离、资源公平

Multipass instances、HostEnvironment、K3sCluster 与 Kubernetes node 是独立身份。HostEnvironment 可持有多个 instance/cluster，单一 cluster 可跨多个其 owner ledger 管理的 guest/node。Infrastructure Profile 的 placement policy 决定 Run 使用 shared cluster pool、Run dedicated cluster 或显式 pinned cluster；不设隐式默认，策略无效时 fail closed。Run binding pin 精确 `k3s_cluster_id + generation`，namespace/RBAC/ResourceQuota/LimitRange/NetworkPolicy/Pod Security/PVC 仅提供集群内隔离，不能替代 cluster identity。禁止按 Worktree/Agent 无策略地复制 VM/control plane。Admission 同时核算 Host 与精确目标 cluster：分别扣除 OS/base、Host safety、cluster safety、非托管负载和各 owner 的未过期 reservations；按 Project 再到 Run/Agent 有界、公平、可取消分配。任一输入未知或不足时拒绝，不从瞬时 free memory 猜余量。

WSL 中非渡口管理的 distro/workload 若没有可靠的可观测用量与可执行硬上限，其资源预算一律视为 unknown，WSL 可安全分配余量也视为 unknown。仍须保留明确 host reserve；遇到 unknown 时拒绝新的 WSL allocation/admission，并提示用户释放或显式管理资源，不能用瞬时空闲量或总内存猜测可承载能力。

Namespace 是组织与权限范围，不能独自证明恶意 Agent code 的强隔离。执行不可信代码须由已验证 Runtime sandbox/VM backend 提供实际隔离；没有该 capability 时禁用对应执行，不把集群 admin kubeconfig、privileged Pod、宿主 root/socket 或任意 hostPath 交给 Agent/Plugin。InfrastructureBackend 与 AgentRuntimeBackend 是独立 provider，可按部署需求组合。

#### Multipass-managed guest 与 Run/Worktree 共用模型

`HostEnvironment` 是宿主级资源/生命周期范围；owner ledger 分别记录 Multipass instance ID/generation、K3s cluster ID/generation、Kubernetes node 与 cluster-to-instance membership。一个 cluster 有一个或多个受管 guest/node，一个 HostEnvironment 可以拥有多个 cluster。`RunInfrastructureBinding` 将 Project/Branch/Run 绑定到有效 placement policy、精确 cluster ID/generation、namespace、ServiceAccount、配额、NetworkPolicy、Runtime Profile 与资源 budget。VM/cluster identity 只由 Manager 创建并经 CAS 管理的 owner record 决定，不从名称前缀单独推断归属。Provider inventory 发现未知 instance/cluster 时只显示为 external/unmanaged，不允许 Star 自动 stop/delete。

WorktreeFocus 由可信目录 owner 解析；workspace bridge 绑定 `(tenant, project, branch, engineering_run, worktree, binding_revision, task_execution_run)`，操作前后重验当前 ACL 与 revision。优先实现经过 digest 校验的有限文件/变更同步或 guest 内 checkout；把宿主 checkout 作为只读输入、guest 侧 overlay/独立 checkout 作为写入目标。若后续选择 Multipass mount，必须先验证 Windows/macOS/Linux 驱动的权限、只读/卸载语义和路径边界，并由原生 Hook 显式授权；不得假设 driver 提供一致 mount 安全语义。

K3s cluster 的 server/node 数量由 versioned profile 明确声明，并受目标 cluster 与 Host 双重容量门控制；单 server 仅是可选的低成本 profile，不是所有 Run 共用的默认 topology。K3s server、agent 与 workload 都占资源；单纯创建 namespace 不会降低 guest 内存消耗，Run quota 必须同时限制 pod CPU/memory/ephemeral storage、并发与日志/镜像保留。当前测试阶段最多保留 2 个已登记 Multipass instance，包含 Stopped/Deleted 记录，因为关机或待 purge 的 guest 数据仍可能占用磁盘；bootstrap 使用 host-local 独占锁串行化完整 inventory 检查与 launch，达到上限或无法解析时拒绝 launch 且不自动 purge。所有 live test launch 必须经此受控路径。当前 Rust contract tests 不启动 Multipass，也不变更现存 VM。CI runner 是另一个明确 owner 的 HostEnvironment，按 ephemeral lifetime 清理其自身实例，不能复用用户工作站的无主全局清理权限。

K3s 基线复用其 containerd；增加 Docker/第二个 containerd/第二个 broker 需要明确用途、端点 owner 和预算。readiness 必须验证 CRI/节点/目标服务可用与期限，不能由 process 存在或端口打开推导就绪。PostgreSQL SoR、owner API/存储过程与 Outbox/Inbox 的现有边界保持一致。

## §3 版本化 Rust 契约
Contract closure: RunInfrastructureBindingSnapshotV2 carries typed ClusterPlacementPolicyV1 and includes its wire value in the deterministic digest. InfrastructureCapacityReservationAcceptanceV2 and InfrastructureReadinessEvidenceV2 carry separate host_capacity_reservation_id and cluster_capacity_reservation_id; validation rejects nil or mismatched references. The current live Multipass test phase is limited to two registered instances total, including stopped/recoverable records; the bootstrap guard serializes inventory check plus launch with a host-local exclusive lock, and never auto-purges. The contract runner is VM-free.


InfrastructureBackendV1 提供 typed discover/probe/plan/create/start/stop/inspect/delete，以及可选 suspend/resume、image import/export 能力。每次返回 capability/version/digest；未知或不支持的操作明确禁用。拓扑实体分别为 HostEnvironment、Multipass instance、K3s cluster 和 Kubernetes node；profile 的 placement policy 必须显式选择 shared pool、Run dedicated 或 pinned cluster，binding 固定目标 cluster ID/generation。Executable 与 argv 由 verified profile 构造，路径/镜像/端口由受权 registry 解析；UI 不能提交任意 shell、宿主路径或 kube context。

`MultipassAdapterV1` 为该契约的首个本地实现，结构化输入 `environment_id`、期望 VM state revision、profile revision/digest、guest image alias+digest、cloud-init digest、资源 reservation、operation/idempotency/correlation IDs、actor 与 deadline；不接受裸命令字符串。子进程只能以 argv 数组启动并复核可执行文件路径/版本；stdout/stderr bytes、运行时长、并发 operation 与 result retention 均有界，超时/取消终止子进程并写入终态 receipt。`list --format json` 必须做 schema/version/size/state 校验。命令 allowlist 仅覆盖由已安装版本 capability probe 确认的 `version/list/info/launch/start/stop/wait-ready`；Multipass 的 [`wait-ready`](https://canonical.com/multipass/docs/latest/reference/command-line-interface/wait-ready/) 只等待 daemon 初始化并可接受请求，不代表 VM 或 K3s readiness。单实例永久回收仅允许 `delete --purge <exact-owned-instance>`，必须与 owner ledger 精确匹配且通过 drain、lease release、retention、Hook 和二次授权；无参数全局 `purge` 与 `delete --all` 永不允许（见官方 [`delete`](https://canonical.com/multipass/docs/latest/reference/command-line-interface/delete/)）。VM Running 由单实例 `info/list` 核验；guest/K3s readiness 通过有版本和 digest 的固定 profile probe 检查 API endpoint、node Ready、CRI 与必要 system workload。若支持 guest probe 的版本提供 `multipass exec`，它只可调用预置固定 executable `/usr/local/libexec/star/guest-ready`，其 argv/env/cwd/输出上限均由 profile 固定；任意用户/Task/Agent 命令不得借用 Infrastructure Adapter 的 exec 权限，实际 Task 命令只经独立 AgentRuntimeProvider 与 sandbox。`shell`、任意 `mount`、任意 `exec`、全局 purge、未授权实例操作与更改全局 driver/settings 默认拒绝。必要 guest setup 命令由固定 cloud-init payload 完成，不由 Agent 注入。

每个 create/upgrade `plan` 显示宿主/VM/cluster 资源增量、placement、image/guest/K3s digest、网络/数据面变化、workspace access 和 rollback/删除范围；native Hook 根据 Project/Worktree effective policy 与 User confirmation gate 给出 Allow/Deny/RequireHuman。长操作使用短事务创建 operation lease，锁外等待 Multipass/K3s readiness，完成后短事务重授权/CAS 与写 Audit/Outbox；不在 DB transaction 中等待 VM 启动。Readiness 分为 Multipass daemon、目标 cluster 的全部 owned VM aggregate、K3s control plane/node/CRI、Agent Runtime sandbox 四个带时间戳的独立事实，不得由 daemon `wait-ready` 或单个 VM Running 推断更高层就绪。Manager 持久化 instance、cluster 与 membership owner/generation，掉电恢复时 reconcile 只对账/接管自己拥有的实例和集群。

InfrastructureProfileV1 分开固定 host_executable_os/arch 与 guest_os/arch，另固定 backend/version、guest image/kernel/k3s/container runtime digest、所需 capabilities、CPU/memory/disk/IO/network budgets、mount/network/retention policy。宿主可执行文件必须匹配 Host OS/architecture；Guest command/payload 由已验证的 guest agent/SSH/Kubernetes API 在匹配 Guest OS/architecture 的环境执行。host_worktree_path → guest_workdir 必须经 Worktree owner 校验并版本化；cwd 使用 guest 内规范路径，不能假定 host 与 guest 路径相同。target、映射或 backend capability 不符时拒绝。

RunInfrastructureBindingV2 固定 tenant/Project/Branch/Run/HostEnvironment、目标 K3s cluster ID/generation、profile placement revision、namespace、runtime identity 与资源租约。Host reservation 与 cluster reservation 由 Infrastructure owner 同一 owner-local admission 原子确认；容量候选在持有相应 owner serialization guard 后重算，不把纯函数候选当成 reservation。命令携带 actor/current grants、command/correlation ID、expected revision 与 deadline；operation receipt 只返回脱敏 ID/state/reason。Runtime readiness 等待期间释放 DB row locks，最终短事务重新授权/CAS；基础设施 operation 不授予 Task/CLI 权限。Kube/VM 凭据由 credential owner 保管，UI/日志/BI 不返回 Secret。

## §4 生命周期、Hook、Loop 与 BI

状态目标为 absent → provisioning → stopped → starting → ready → draining → stopped → deleting → absent，错误进入带 reason 的 degraded/failed；永久删除仅在独立确认/保留门后触发，suspend 只对声明并验收 capability 的 backend 开放。创建/升级/网络/mount/删除均经 native Hook、plan、授权和最终复核；插件只能建议，不可绕过安全门。

按需启动与 idle stop 受 durable lease、Agent/Task/Loop/DB/Outbox 活动和 checkpoint/备份状态控制。停止前拒绝新准入并 drain 当前操作；活跃或 unknown 不能自动销毁。Schedule Loop 使用唯一 occurrence/租约机制，不另建 cron owner；重启恢复幂等 command 并重验 scope/fence。Upgrade 固定版本、迁移/备份与 rollback receipt；不能假定跨 hypervisor 版本 snapshot 可恢复。

事件固定 environment/Run/profile/version/digest、operation、资源/延迟摘要、Hook decision、failure/drain reason；脱敏 append-only Audit 与 Outbox 联动 BI/Benchmark。BI 建议经已生效 native policy 采纳；不能直接扩大内存、权限或重启用户环境。

## §5 低内存与操作所有权

K3s 官方要求 server 最低 2 cores / 2 GB RAM，且基线不含 workload；参见[官方 requirements](https://docs.k3s.io/installation/requirements)。现有单机 PoC 使用 4 vCPU / 8 GiB / 28 GiB guest，在 31.8 GB 主机上实际运行 K3s 与 19 个 GitOps/基础设施 Pod；详见实跑报告。它只证明该固定 host/profile 可启动并达到当前服务 readiness，不提供 Star 桌面进程树、Agent workload、并行 fairness 或峰值 RSS 基准。2 vCPU / 4 GiB 仍只是另一个待测 PoC profile，不代表产品最低配置或已测可行性。测试须纳入 PostgreSQL/NATS/真实 Rust 服务及 1/2/4/8 Agent 固定负载，测峰值、p95/取消、冷启动与长运行漂移，并扣除 OS/宿主保留量；结果出炉前预算保持 provisional。

WSL2 .wslconfig 的 memory/processors、autoMemoryReclaim 等是[影响所有 WSL2 distro 的全局设置](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)。wsl --shutdown 会立即终止所有运行中的 distro 和 WSL2 utility VM（[官方说明](https://learn.microsoft.com/en-us/windows/wsl/basic-commands#shutdown)）。修改 .wslconfig 或执行全局 shutdown 前必须在产品界面明确说明影响范围并获得用户显式授权；禁止静默修改或把全局操作当作常规回收。只对明确属于渡口的 distro/VM/namespace/PVC 执行其余生命周期操作。非渡口 WSL workload 的 cap 不可证实时按 §2 视为 unknown、保留 host reserve 并拒绝准入；不得声称资源隔离已达硬限。

Rust desktop UI 不直接持有 Multipass CLI session、VM logs 或 Kubernetes watch 全量历史。一个按需运行的 Host Infrastructure Manager 使用普通用户权限和窄 typed IPC 操作 Multipass CLI；若平台要求额外授权，由 OS/Multipass 明示授权，不提升整个 GUI、Agent 或 Plugin 权限。Manager 使用共享 Tokio executor、有界 per-host operation queue、公平 admission、deadline/cancel/drain、分页状态窗口与有界 log cache；耗时 hypervisor/Kube/IO 在 UI 线程外执行。每个 Host/environment 共享一份按 digest 缓存的 guest image/K3s layers，并设容量与 TTL；不按 Run/Worktree 重复下载全镜像。Host RAM 预算必须同时计算桌面进程树、base OS、Multipass VM 分配、K3s/containerd、guest workloads 与未托管用量；unknown load 作为 unknown capacity，不过量承诺。Suspend/stop 是否释放内存需实测，磁盘/数据库持久性须有明确 retention 与备份；无主操作须有 reconciler，失败不会留下静默活跃进程。

## §6 持久化分类与后续 schema 门

以下按数据 owner 分类。标为 Existing 的 Project/Run 行已由 Run/Execution migrations 建表；Infrastructure owner 六表 additive schema 已在本阶段创建并通过 disposable PostgreSQL 验证，但未部署到目标数据库且没有生产 writer/consumer/grants。其余 Host/instance/cluster master、Manager operation/readiness store 等仍为规划对象。分类不把现有 Run 表误作 Host capacity，也不把宿主 PoC 当作产品存储实现。

| 拟分类对象 | 初步分类 | 设计要求 |
|---|---|---|
| Profile/backend trust、VM image/cloud-init/K3s catalog、HostEnvironment、Multipass owned-instance ledger 与 Project/Run binding | Master (planned) | SCD2/version/digest、no physical delete、instance owner/generation 明确、独立 role/policy/capability 分类；目标库完整 RLS 与 audit |
| Project/Run execution quota revision | Master | Existing Run/Execution owner SCD2 limit; no physical delete, audited revision and tenant RLS. |
| Project/Run quota audit and reservation lifecycle events | Transaction | Existing immutable, tenant-scoped facts; append-only audit and reservation lifecycle evidence. |
| Project execution admission lock | Work | Existing short coordination state with 30-day expiry/index; tenant-scoped pruning worker is not located or verified and remains a retention gate. |
| Project/Run resource reservation | Work | Existing Run-owned bounded lease, with pending/active/released states and lease_expires_at; not Host VM/K3s capacity. Current DELETE guard and parent-Run retention leave terminal physical cleanup unresolved. |

### §7.5 Phase 9F4D-3C2：owner transaction admission and paired capacity reservation

`PostgresInfrastructureOwnerAdmission::admit_inbox` is an owner-store primitive for an already persisted demand. In one transaction it activates the restricted owner role and tenant RLS scope; reads the immutable Host/cluster lock scope; obtains the tenant+resource advisory locks in deterministic key order; locks and reloads the Inbox row; verifies typed payload, indexed columns, payload/binding digests and deadline; and checks terminal receipt replay before any state transition. Expired leases do not consume headroom: Host and exact-cluster held reservations are independently summed from the owner ledger only when `lease_expires_at > transaction_now`. The candidate evaluator still requires fresh, exact-scope Host and cluster observations and a matching profile request.

On acceptance the same transaction inserts the paired reservation bundle with two distinct reservation IDs, appends the held lifecycle event and accepted receipt, marks Inbox terminal, and writes versioned owner Outbox plus separate delivery state. Unknown/stale/insufficient capacity returns bounded retry without creating a reservation; malformed or mismatched generation/scope is terminally rejected. Exact terminal replay validates demand digest and verifies the reservation pair. A disposable PostgreSQL 18.6 test covers concurrent demands on the same Host/cluster, one accepted pair plus one retry, idempotent replay, generation mismatch rejection, and capacity reuse after lease expiry.

The transaction is tenant-scoped because all six owner tables use FORCE RLS. Its ledger does not see another tenant's reservations, and its advisory locks are tenant-qualified. Therefore it cannot safely allocate a physical Host or cluster shared across tenants. Such placement remains fail-closed until a system-wide allocator with explicit global capacity ownership, isolation and lock identity is designed and verified. Within a tenant, explicit profile placement still selects shared pool, Run-dedicated or pinned cluster; no product topology default is changed.

This is not a production consumer or execution path. The trusted binding/placement resolver, provider observation producer, per-trigger ACL/currentness fence, target DB provisioning/login activation, durable owner Inbox/Outbox worker, retry/reaper/reconciliation, Manager/Multipass/K3s lifecycle, BI/Benchmark, Runtime sandbox/workspace bridge and Schedule executor remain open. No public admission endpoint is mounted, no TaskExecutionRun is started, and the current Multipass inventory cap remains two registered instances total due to disk capacity; this integration gate starts zero VMs.

### §7.6 Phase 9F4D-3C3：Persisted Provider Profile and profile-derived capacity request

`infrastructure.provider_profile_revision` is the Infrastructure owner's tenant-scoped Master source for a versioned provider profile. Each revision fixes `schema_version`, tenant/profile/revision identity, provider kind, placement policy, Host capacity vector, exact-cluster capacity vector, deterministic `profile_digest`, validity interval and actor. Revisions are SCD2: a current row may be closed exactly once by the current tenant actor, but its business content cannot be edited and the row cannot be physically deleted. `provider_profile_revision_event` is a separate append-only Transaction table for `created` and `superseded` facts. Both tables use ENABLE + FORCE RLS on `tenant_id`; the restricted owner role can read both and cannot mutate either.

`PostgresInfrastructureOwnerAdmission::admit_inbox` no longer accepts a caller-supplied `InfrastructureCapacityRequestV2`. Inside the existing owner transaction and tenant RLS scope it loads the exact profile revision referenced by the persisted demand, decodes bounded DB values into the typed profile, recomputes the deterministic profile digest, and compares it with the stored digest. It then checks tenant/profile/revision/provider/placement and the Run binding's pinned digest before deriving both resource vectors. Missing profiles, invalid DB rows, unsupported schema, binding mismatch or a persisted digest mismatch fail closed before any reservation. Persisted digest mismatch is a terminal rejection with receipt/Outbox and no reservation.

The disposable PostgreSQL 18.6 runner now applies the schema, grants and profile migrations twice each; verifies 8/8 Infrastructure tables FORCE RLS, tenant isolation, owner read-only profile grants, one-time SCD2 closure, append-only audit events and all five SQLx admission cases (including digest mismatch). All 17 runner steps passed and the temporary cluster stopped and was cleaned. No Multipass instance was started; the inventory cap remains two registered entries total because of disk capacity.

This closes only the persisted profile source and derivation boundary for the existing tenant-scoped admission primitive. The profile editor/current-profile resolver, immutable Run binding resolver, provider observation producer, production ACL/currentness fence, global cross-tenant allocator, target DB provisioning/login activation, durable Inbox/Outbox consumer, retry/reaper/reconciliation, Manager/provider, readiness producer, BI/Benchmark, Runtime sandbox/workspace bridge and Schedule executor remain open. Do not enable a worker, TaskExecutionRun or Task Card CLI execution from this slice.

### §7.7 Phase 9F4D-3D1：Global physical Host and exact-cluster capacity ledger

The tenant-scoped reservation bundle cannot prevent two tenants from oversubscribing one physical Host or one exact K3s cluster. Migration `2026-10-10-infrastructure-physical-capacity-ledger.sql` adds `capacity_physical_reservation` (Work) and `capacity_physical_reservation_event` (Transaction). These global rows deliberately omit `tenant_id`; both tables use ENABLE + FORCE RLS with exactly the restricted `star_infrastructure_owner` policy. Existing tenant Inbox, paired bundle, receipt, audit facts and Outbox retain tenant FORCE RLS.

`admit_inbox` takes tenant Host/cluster keys and physical Host/cluster keys in one deterministic sorted/deduplicated order before it reloads and evaluates the demand. The global Work table is the source for held, unexpired physical reservation aggregation. Admission writes the global reservation and `held` event in the same Infrastructure-owner transaction as the tenant bundle, tenant event, receipt, Inbox transition and Outbox/delivery facts. A database AFTER-trigger appends a physical Transaction event atomically for each valid `held → released/expired` Work transition; the trigger requires `app.actor_id` and the owner transaction sets it from the Infrastructure service actor. Terminal Work cleanup remains bounded by the 24–25 hour retention guard.

No live resource is created or launched by this slice.

### §7.8 Phase 9F4D-3D2：bounded paired reservation expiry

`PostgresInfrastructureOwnerAdmission::expire_due_reservations` is a tenant-scoped owner-store primitive with `1..=64` maximum batch size. It scans held tenant bundles whose lease is elapsed according to PostgreSQL `clock_timestamp()`, orders them deterministically, and processes each candidate in a separate transaction. Each transaction acquires the same globally sorted and deduplicated tenant/physical Host/exact-cluster locks used by admission, reloads the tenant bundle and global physical row `FOR UPDATE`, and verifies every reservation ID, Host/cluster identity, generation, resource vector, capacity digest, observation timestamp, lease timestamp and state before mutation.

Only a consistent pair that is still held and expired transitions to `expired`. The same transaction updates both Work ledgers, inserts the tenant lifecycle Transaction, lets the existing database trigger append the global physical Transaction, and writes one immutable `capacity_expired` owner Outbox event with its pending delivery row. A candidate whose lease was renewed or whose state changed is skipped idempotently. A missing or mismatched physical pair aborts the transaction; the two ledgers cannot diverge through this operation. PostgreSQL time is authoritative for both admission deadline and expiry decisions, avoiding application/DB clock skew.

This adds no table or migration and does not change the cumulative 10-table W/T/M classification. It does not change the selected topology: Multipass manages one or more Linux guests running K3s, with no Docker Desktop prerequisite. It is not a scheduled worker, cross-tenant scanner, Outbox delivery consumer, Run/Execution outcome consumer, active Agent Runtime lease-renewal protocol, VM stop/delete operation or K3s cluster lifecycle. The current integration suite starts zero Multipass instances; test inventory remains limited to two registered instances total, including Stopped/Deleted. Schedule retry/resume and TaskExecutionRun transitions remain owned by their existing Run/Schedule owners and stay fail-closed until those consumers are implemented.
