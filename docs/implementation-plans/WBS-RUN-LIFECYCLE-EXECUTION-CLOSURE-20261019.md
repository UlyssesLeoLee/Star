### Project and Repository authority decisions (confirmed 2026-10-26)

- Star's native Project owner is the canonical owner for Project identity, membership and Project-to-Repository associations. A Project supports 0..N repositories; a default repository is only a UI preference for ordering/preselection.
- Before removing a Project-to-Repository association, migrate and verify every active Run/Worktree reference to another repository in the same Project, or explicitly retire the affected checkout. If migration or verification fails, fail closed and retain the old association and binding; never silently detach active work.
- Provider profiles are deployment-specific: Vercel uses Neon; K3s uses PostgreSQL running inside Multipass-managed Linux VM(s). They do not automatically synchronize data. The current test inventory remains capped at two Multipass instances, counting stopped/deleted records; no automatic purge and no Docker Desktop prerequisite.
- Preview data must be schema-only or sanitized. Neon branches isolate writes but may inherit the parent branch's schema and data; production data is not safe for Preview merely because the child branch is isolated.
- Neon pooled connections use transaction-mode pooling. The platform documentation lists session-level `SET`/`RESET` as unsupported; whether Star's explicit-transaction `SET LOCAL` RLS context works with the selected Neon endpoint and Rust driver remains an acceptance gate. Use a separate direct endpoint and migration identity for migration jobs; never run DDL in request functions.
