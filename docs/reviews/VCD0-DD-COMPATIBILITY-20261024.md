## 4. Owner, authorization, and data-flow gaps

The future design needs one explicit path and must not describe an alternate business authority:

```text
Protected Preview or Production Web/BFF
  -> actual host session contract and route allowlist
  -> Star Rust API / authoritative Star Owner (current Run/Worktree authorization)
  -> owner-local transaction, idempotency receipt, audit and transactional Outbox
  -> Star-owned consumer / Run-Execution owner
  -> Infrastructure owner reservations and trusted Rust Host Infrastructure Manager
  -> bounded Multipass-managed Linux guest(s) running the bound K3s cluster and sandbox
```

Vercel Preview must use isolated credentials and data and must not call production Owners, Schedule triggers, or mutation endpoints. Production BFF/Rust HTTP adapters remain stateless entry/transport layers and may not bypass the Star Owner. A timed-out mutation stays `state_unknown` until the same owner and same idempotency key provide authoritative status; an HTTP status or transport connection does not prove task execution or success.

Before any future VCD-3 endpoint can be specified, its detail design must name the actual Star Owner and endpoint contract, host-session issuer/audience and Run scope, owner transaction and Outbox/Inbox boundary, durable receipt lookup, audit/BI correlation, resource limits, retry/cancel behavior, and failure response. The current candidate describes abstract owners/generations but does not map each endpoint to verified Star owner APIs or their existing persistence contracts. It also proposes capabilities/auth routes whose ownership is unresolved.

For Schedule, name the immutable `run_as_actor_id`, current Project/Run permission and execution-capability recheck on every trigger/retry/resume, the bound `RunInfrastructureBinding`, and the separate Run/Execution and Infrastructure owner reservations. Cron must not reserve host/cluster capacity or start an executor. For Agent/Task CLI, keep the task's bound Worktree checkout and CLI focus, native Rust Hook gates, sandbox readiness, cancellation/recovery, independent verification, and result evidence in the Star execution path.

The draft's B-Independent assumptions make several of these flows appear possible by creating new owners and data stores. Replacing them with an explicit Star owner mapping is required; additional Owner/DB/worker tables or a second runtime are not a harmless detail-level choice.

## 5. Minimum alignment edits for a future detailed design

1. Rebase the design premise on the current `dev` SRS v0.3 and WBS v4.17. Remove claims that a v2.0 Vercel SRS/basic design/ADR/test suite is current or approved. Keep all implementation/deployment status `NOT_RUN` until there is real evidence.
2. Rewrite §§0-1 as one optional hosting path: protected Vercel Preview and Production frontend/BFF, with Star Rust Owners and Multipass-managed K3s remaining authoritative. Remove Track A/Track B as product modes, B-Independent/B-Attached, B-owned Owners/DB/worker/scheduler/VM, and B-owned execution alternatives.
3. Reduce §2-4 to environment isolation, the verified host-session contract, same-origin BFF request checks, and Owner-side current authorization. Do not create an independent Identity Owner or authorize through BFF headers. Preserve Preview's no-production-secret/data/side-effect invariant.
4. Rewrite §5 so Project → Engineering Run → Worktree → Branch and current Star APIs/Owners define business truth. Keep Schedule as Star-owned; Cron is optional wake-up/reconciliation only. Add immutable `run_as_actor_id` revalidation and fixed RunInfrastructureBinding at each unattended trigger/retry/resume. Keep terminal/Canvas WSS, Agent execution, native Hooks, task CLI and local Worktree filesystem in Star's authoritative execution plane.
5. Keep §5.6/§5.8 owner-local transaction, Outbox/Inbox, idempotency and audit invariants only after mapping to real Star repositories. No second DB, migrator, scheduler, consumer or authority; any new table must go through the existing W/T/M and RLS review.
6. Limit §6 to the isolated VCD-2 target-account/plan Rust Runtime proof with no production data or business writes. State unknown Rust limits/features as unknown. VCD-3 stays conditional on VCD-2 PASS and WLD-0/WLD-6, and only an allowlisted thin adapter to an existing Star Owner may be designed.
7. Correct §5.3 and the Rust feature claims: WebSocket GA applies to Functions overall, not proven Rust support. Keep Star's realtime gateways authoritative; any Rust WS/streaming evaluation belongs to the isolated proof and cannot enable production behavior without explicit evidence.
8. Correct §§5.5/7.5 and review AR-13 based on current official Cron pages: rollback restores the target deployment's Cron definitions and the disabled setting persists. Continue verifying the active Cron configuration and owner schedule state during rollback because scheduling truth remains with Star.
9. Regenerate §10 against only FR-VC-001..021, NFR-VC-01..08, AC-VC-001..013, GAP-01..11 and WBS VCD-0..4. Remove invented/absent IDs and unsupported performance, coverage, and rollback thresholds unless they first become approved requirements.
10. Keep Vercel-specific work phased: VCD-0 design set; VCD-1 protected frontend; VCD-2 isolated Rust proof; VCD-3 conditional owner-backed adapters; VCD-4 operational acceptance. Do not mark a phase complete from static prose.

## 6. Current official-platform fact check

Reviewed 2026-10-24:

- [WebSocket support is now generally available](https://vercel.com/changelog/websocket-support-is-now-generally-available) states that WebSocket support in Vercel Functions became generally available on 2026-10-20. It does not specify the Rust runtime.
- [Using the Rust Runtime with Vercel Functions](https://vercel.com/docs/functions/runtimes/rust) still labels Rust Runtime Beta. Its feature table (last updated 2025-12-08) has blank support values for several features and no WebSocket row. Rust-specific support therefore remains unproven and must pass VCD-2 on the intended account/plan.
- [Managing Cron Jobs](https://vercel.com/docs/cron-jobs/manage-cron-jobs) (updated 2026-08-11) says rollback restores the Cron definitions associated with the target deployment; the project's Disable Cron Jobs setting persists. [Instant Rollback](https://vercel.com/docs/instant-rollback) (updated 2026-07-07) says the same. The two current pages are aligned; a separate newer Cron-rollback behavior announcement was not found in the Vercel changelog search. DD §5.5/§7.5 and prior review AR-13 should not preserve the former conflict claim.
- The same Cron management page says failed invocations are not retried and overlapping/duplicate invocations can occur. This supports the SRS rule that Cron is only a best-effort wake-up/reconciliation signal, never Schedule truth or the executor.

## 7. Carry-forward verdict

**Do not merge or adopt `DD-STAR-VERCEL-DEPLOY-001.md` as-is.** It is an untracked, unapproved v2.0 candidate built around a second parallel business/execution platform, while current `dev` approves only an optional protected frontend path and a Rust HTTP adapter candidate gated by VCD-2. That difference changes authority, data ownership, execution, and Schedule semantics; it is not a documentation-only naming mismatch.

Carry forward only the bounded security/transport/Owner invariants in §2 above as source notes for the VCD-0 rewrite. First author a new detailed design against current SRS v0.3 and WBS VCD-0..4, remove unapproved topologies, repair the traceability and platform facts, and leave all deployment/runtime/production gates open. This review adds no requirements and claims no implementation.
