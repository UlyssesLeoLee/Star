Do not place Project identity or association authority in SCM, Run Directory, or Worktree tables.

## 2. Recommended owner boundaries

1. **Star-native Project owner (selected canonical owner):** owns Project identity, durable Project-member authorization facts, and ProjectRepository associations. Its versioned owner API is the canonical path for identity, current membership/authorization checks, and association operations. The current `ProjectRepository` implementation remains in-memory; durable persistence and API contracts are not implemented.
2. **Authorization-consuming owners:** Run Directory and Worktree/Host must consume current Project-owner authorization facts through the approved owner contract; the existing Run Directory read/lock grant is not permission-write authority. The exact API surface, cache/version/reauthorization rules, and migration from current direct read grants remain to be designed.
3. **SCM owner:** owns stable `RepositoryId`, Repository master revisions, and provider metadata. Project membership references the stable RepositoryId without modifying SCM facts. Repository-master revisions and Project links are distinct histories.
4. **Run Directory owner:** owns Engineering Run repository bindings and Run↔Worktree references. It is a source of active references that must be included in migration reconciliation. A migration command, transaction boundary, Outbox write boundary, and receipt contract are not established by the current implementation.
5. **Worktree/Host owner:** owns local checkout identity and trusted root/path resolution; its Worktree bindings and actual checkout are relevant migration evidence. Whether this owner performs the migration, what transaction boundary applies, and how it emits durable audit/Outbox evidence are not established by the current implementation.

Do not use one shared cross-owner database transaction or direct cross-owner table writes. The current `RunWorktreeLifecycleProvider` contract requires the provider to use the binding owner and forbids direct writes to its tables. For ProjectRepository migration, the per-owner grouping of binding changes, audit, and Outbox; their atomic commit boundaries; and cross-owner orchestration/commit ordering remain unspecified.

## 3. Migration-before-unlink contract

The confirmed policy is **0..N Repository associations per Project** and **migrate all active Run/Worktree references before unlinking an association**. Each active reference must move to another currently authorized active Repository association in the same Project, or the Project owner must explicitly retire a reference that no longer needs a checkout. The source association and existing bindings remain valid until migration verification succeeds; an active retiring fence may block new references. These invariants do not settle which eligible destination is selected, the migration owner topology, or transaction design:

1. While any active Run/Worktree reference still points to the source association, the association remains linked and valid. Unlink is unavailable until every such reference has been migrated and its destination binding verified.
2. If a migration step fails, times out, is unauthorized, or cannot verify its destination, no unlink occurs and the old association remains valid so its existing references continue to resolve. Partial progress must not be reported as migration completion.
3. Before unlink, durable audit and Outbox evidence must be available for the completed migrations, and a complete, revision-aware reconciliation across every relevant Run and Worktree/Host reference owner must prove there are zero active references to the source association. A raw count, partial page, stale owner revision, or missing owner response is insufficient.
4. The unlink operation must use concurrency-safe revision checking. Any revision conflict, newly observed source reference, unverified destination binding, missing durable evidence, or incomplete reconciliation aborts unlink; re-read and reconcile before retry. The concrete admission fence and CAS/serialization protocol are not yet specified.

Open design items: selection among the eligible same-Project active authorized associations (or explicit retirement criteria), authoritative owners/stores to enumerate, admission of new bindings while a retiring fence is active, per-owner transaction grouping for binding/audit/Outbox, evidence durability/atomicity, and cross-owner orchestration/commit ordering. Do not transition the old association or existing bindings to an invalid state before migration completes; failure paths retain them and deny unlink.

## 4. Default preference and data boundaries

- Store an optional default only within the Star-native Project owner's authority.
- Clearing or changing the default is an explicit Project preference update. Unlinking the association currently selected as default must not silently auto-select another repository; a default never acts as an implicit Run binding.
- Candidate relation data belongs to the Project owner as versioned Master/SCD2 history; owner commands/idempotency leases are bounded Work data; append-only audit and Outbox events are Transaction facts. Do not put payloads or short-lived retry state into the SCM Repository master.
- A cross-tenant link, unknown Project/Repository, unavailable target, or incomplete authorization must fail closed. The association lifecycle states are not established. Do not invent a FK to a Project table that does not exist in the examined migrations. Before relying on relational FK enforcement, establish the authoritative Project identity store and a tenant-scoped reference to stable RepositoryId; otherwise define a versioned owner contract with durable validation evidence.

- **WLD1-R2 — final unlink:** prove a complete revision-aware zero-reference reconciliation, durable audit/Outbox evidence, verified destination bindings, failure/retry behavior, and concurrency-safe revision checking under the target PostgreSQL role/RLS configuration. The concrete fence and commit protocol remain design gates.

Required tests/evidence (not run by this audit):

- Target PostgreSQL migration replay, owner role grants, FORCE RLS, cross-tenant isolation, revoked Project role, and durable audit/Outbox evidence. Transaction atomicity must follow the separately approved boundary design.
- 0..N links; optional default preference behavior; concurrency-safe revision check for unlink. Add/replay and detailed lifecycle-state cases must follow the separately approved relation/API contract.
- Inject failure at each migration step and prove the source association remains linked and valid, existing references still resolve, and unlink is rejected.
- Prove migration completion from a complete, revision-aware inventory of every authoritative Run and Worktree/Host reference source: every previously active source reference must have a verified destination binding, and a fresh reconciliation must show zero active source references. Partial pages, stale revisions, unknown owner coverage, or unavailable stores fail closed.
- Durable audit and Outbox evidence must support checking that migrations completed and destination bindings were verified. Which owner emits each record, when records become durable, how they relate atomically to binding changes, and how owners coordinate commits remain OPEN design questions.
- Race a new source reference and another link revision against migration/unlink. Demonstrate concurrency-safe revision checking prevents unlink based on stale zero-reference evidence; specify the admission/fence behavior in a later design decision.
- Hostless Run remains supported; removing a ProjectRepository link cannot introduce a remote Branch prerequisite.
