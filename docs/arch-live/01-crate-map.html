8 个家族。分族的依据不是"感觉上像一类"，而是 依赖方向：上层可以依赖下层，下层不得反向 import 上层。

04 放置决策树

判断顺序（自上而下，命中即停）

1. 是"业务规则/状态机"吗 → 归到已有 domain-*；没有合适 bounded context 才新建
2. 是"跨域机制"吗（锁/事件/缓存/队列/计量）→ star-*
3. 是"Worktree 图谱"吗 → 14 个 canvas crate 之一
4. 是"同一 Task 的另一种视图"吗 → 5 个 view crate + shared-task
5. 是"Agent 关系"吗 → ARG 三层
6. 是"纯函数且前端也要用"吗 → 加 -wasm 桥
7. 是"要独立起进程"吗 → 进程面 crate（自带 axum server）
8. 以上都不是 → 先别建 crate，放进最接近的既有 crate

三条硬约束

① 依赖单向。上层可依赖下层，反向禁止。

② 跨域只能经由显式契约。不要在 star-* 里 use domain_work_item::…； 要协作就走事件（star-eventbus）或 saga 的显式流程。

③ 新 crate 的默认命运是骨架。新 crate 多数只含 Port trait + 实体 + 少量 UT； "有 crate" 不等于 "有实现"，判断实装度请看第 03 节。

证据：家族划分依据与逐族清单
  • 家族清单由 python scripts/automation/arch_live_doc_check.py --emit-chips 从 crates/ 目录实扫生成，不是手写维护的列表。
  • worktree-canvas 的 14 个成员表直接来自 crates/worktree-canvas/src/lib.rs 的模块清单（facade re-export 14 个 sibling crate）。
  • ARG 三层与 5 视图的定位来自 Cargo.toml members 段的注释（每个 member 注册时都写明 per 哪份设计文档与哪条守门）。
  • 支撑层的 Port trait 形态见 crates/api/src/lib.rs：pub trait ApiGateway / pub trait ApiQuery。
