k3s 上的三个 namespace 与一条边缘

本地部署是 k3s + kustomize：star-system 跑业务服务，star 跑 BFF 边缘， 另有 star-system 内的 canvas 四进程。边缘统一用 envoy 独立 Deployment， 不用 nginx、不用 istio sidecar。

02 envoy 的 5 条业务路由

边缘不做业务判断，只做前缀分流。不在白名单的一律 404，没有隐式兜底——这条让"某个前缀配错了"变成显式故障， 而不是悄悄穿透到某个不该暴露的服务。

/——catch-all 404（Not Found）
TLS 走 SDS 自动轮换：证书由 cert-manager 签发，envoy 通过 sds_cluster（gRPC，:8081）拉取， 配置里不落盘任何证书或密钥——符合"配置不存 secret"的硬约束。
已发现的不一致（建议修）：envoy 的 star_mcp_cluster 指向 port 3000， 而 star-mcp 二进制自己的默认 bind 是 127.0.0.1:8080（可用 STAR_MCP_BIND_ADDR 覆盖）。 两者只有在部署时显式把 STAR_MCP_BIND_ADDR 设成 :3000 才能对上； 现有 k3s-local 资源里没有为 star-mcp 提供 Deployment，因此这条路由当前无后端。 这类"配置与代码默认值不一致"的点，光看任一侧都发现不了——两处必须一起看。

04 容器安全基线

所有 Deployment 统一施加的 securityContext，这是可验证的安全下界：

四个强制项

allowPrivilegeEscalation: false
readOnlyRootFilesystem: true
runAsNonRoot: true · runAsUser: 65532
capabilities.drop: ALL

资源与显式声明

requests: 100m CPU / 128Mi
limits: 500m CPU / 512Mi
istio sidecar: sidecar.istio.io/inject: "false"
镜像: canvas 走 GHCR :dev；本地服务走 :local + Never

为什么显式写 istio-injection: false：namespace 层的 istio-injection: disabled 标注在 canvas yaml 里已存在， 但 Deployment 上再显式声明一次，可以避免"后来有人给 namespace 打开了注入"导致所有容器被塞进 sidecar。 架构决策（envoy 独立 Deployment，不用 sidecar）应该写在每个 Deployment 上，而不只写在文档里。

05 Helm chart 的真实状态

不要把 deploy/helm/star 当成可用发布路径。该 chart 目前只有少量模板 （NOTES.txt / _helpers.tpl / secret.yaml 等占位）， 8 个服务里只有 star-api-rest 有真实可运行的 manifest。其余 crate 多数只有 lib.rs 没有 main.rs （context / sa / sse / webhook / cache / saga），star-cli 与 star-ops 是 CLI / 运维入口而非常驻服务， 所以没有对应 Deployment。当前唯一诚实的部署路径是 deploy/k3s-local（kustomize）。

06 本地拉起顺序 有顺序要求

1 / 6
1 检查 container runtime 就绪
apply 任何 yaml 之前，先确认 k3s 没有持续输出 "Skipping pod sync"。非 0 就先 restart k3s。容器运行时就绪前 apply 的 pod 会 100% 卡 Pending（与 namespace 无关）。
2 重启后等 60s
k3s 拉起后 kubelet 子组件异步就绪。立即 apply 会撞上 30-60s 窗口期，表现为"所有 pod 都 Pending"。
3 先 disable port-forward 服务
Restart=on-failure 的 systemd user service 会在 pod 未 Ready 时以 5s 周期疯狂重启，并刷出大量 "no route to host" 502 噪音。apply deployment 前先 disable。
4 安装 sealed secrets
用 install-sealed-secrets.sh 装控制器与证书，再解封 secret。仓库里不提交明文 secret。
5 kustomize build + apply
deploy/k3s-local/kustomization.yaml 聚合 3 个资源：bff-deployment / star-api-rest-deploy / envoy/。注意它刻意跨两个 namespace，没有 base overlay。
6 验证后再 enable port-forward
pod Ready 之后再 enable --now，然后按端口表逐个探活：8443 → 8081 → 3000 → 8080。
证据：拓扑、端口与顺序的出处
  • envoy 路由 / cluster / 超时 / 熔断 / SDS：deploy/k3s-local/envoy/configmap.yaml。
  • star-api-rest Deployment + Service + NodePort：deploy/k3s-local/star-api-rest-deploy.yaml（含 namespace star-system）。
  • BFF + bff-envoy + 显式 sidecar.istio.io/inject: "false"：deploy/k3s-local/bff-deployment.yaml（ns star）。
  • canvas 四进程端口与镜像：deploy/canvas-game-k3s.yaml。
  • Helm chart 现状：deploy/helm/star/templates 实际内容 + star-api-rest-deploy.yaml 头部注释（明写 chart 为 stub）。
  • 拉起顺序：本地实证得出的 3 条防御（container runtime 检查 / 60s 等待 / port-forward 先 disable），已固化进 docs/reports/PHASE-K3S-STAR-MOCK-IMPL-REPORT.md。
  • star-mcp 默认 bind：crates/star-mcp/src/main.rs（--bind-addr 默认 127.0.0.1:8080，env STAR_MCP_BIND_ADDR）。
