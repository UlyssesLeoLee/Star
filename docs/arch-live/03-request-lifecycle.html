02 逐步演示

1 / 13
1 入口收敛 信任边界 ①
请求可能来自浏览器、CLI、MCP、Webhook。此时它完全不可信：没有解析出合法 bearer token 之前，handler 代码一行都不该跑。
envoy 只按 5 条前缀路由，不做业务判断；不在白名单的一律 404（无隐式兜底）
2 边缘分流 + 重试
按前缀落到对应进程。/api/v1/ 有重试策略：retry_on 5xx,reset,connect-failure，3 次，每次 5s 超时；该 cluster 还配了熔断阈值（max_connections / pending / requests = 1024）。
deploy/k3s-local/envoy/configmap.yaml · cluster star_api_rest_cluster
3 OAuth2 校验 → Claims → AuthUser
校验 bearer token（本地 keypair 验签，授权流程走 PKCE）。通过后从 Claims 构造 AuthUser，字段只有 4 个：user_id、tenant_id、roles、scope。
crates/star-api-rest/src/auth/oauth/{middleware,keypair,pkce}.rs · auth/mod.rs:From<Claims>
4 axum extractor 注入 actor
handler 签名里出现 AuthenticatedUser(actor): AuthenticatedUser，就意味着没有合法 token 的请求根本进不到这个函数。这是编译期保证，不是运行时约定。
pub struct AuthenticatedUser(pub AuthUser) // axum FromRequestParts extractor
5 scope 与 role 校验 403
require_scope(user, "worktree:read") 按空白切分比对，缺任一即 403，并带 WWW-Authenticate: Bearer … error="insufficient_scope"。另有 require_role()。空 scope 拒绝一切（已有单测锁定该行为）。
auth/oauth/middleware.rs:629 require_scope · require_scope_with_empty_scope_denies_all
6 actor 有效性 401
validate_actor() 拒绝 nil 的 user_id 或 tenant_id。这一步存在的原因：nil UUID 能通过大部分类型检查，却会击穿所有按 tenant 过滤的查询——必须在入口拦住。
group_api.rs:622 validate_actor → GroupApiError::unauthorized()
7 事务开始 + RLS 前置 隔离点
进入事务后的第一条 SQL 就是把租户写进会话变量。true 表示事务局部（提交即失效，不污染连接池）。此后所有查询被行级安全策略强制过滤——租户隔离由数据库保证，不靠应用层自觉。
SELECT set_config('app.tenant_id', $1, true) — group_api.rs:584 set_tenant
8 项目角色绑定复核 404
查 permission.project_role_binding，要求 valid_from ≤ now() AND valid_to IS NULL，并用 FOR SHARE 拿行锁防止并发改绑。查不到返回 404 而不是 403——避免通过状态码探测资源是否存在。
group_api.rs:596 active_binding · permission.project_role_binding
9 领域规则执行
业务规则在 domain-* crate 内，通过 Port trait 调用；具体实现（InMemory / PG）由 infrastructure 的 registry 提供。状态机非法迁移在这里被拒，不会到 SQL 层。
ApiGateway / ApiQuery Port trait · crates/infrastructure/src/registry_real_pg.rs
10 并发控制 多 Agent 关键
同一 Worktree 可能被多个 Agent 同时操作。三种手段并存：DomainMutex 语义锁、VersionCAS 乐观锁（版本号不匹配即冲突）、PgAdvisoryLock 数据库锁。所有获取都写 LockAuditLogger，冲突可事后复盘。
crates/star-mutex/src/ · worktree 响应含 locked / git_lock.state / version 字段
11 单事务写三张表 一致性
写操作在一个事务里落三样东西：当前态（如 task_lifecycle_current）、审计（task_lifecycle_audit）、outbox（task_run_outbox）。这样"状态改了但事件丢了"不可能发生——事件与状态同生共死。
multica.task_lifecycle_current / _audit / task_run_outbox · canvas_group_outbox · schedule_rule_outbox
12 幂等键去重 重放防护
重复提交由 command idempotency 表挡住：同 key 直接返回首次结果，不重复执行副作用。SCM 侧还区分了 IdempotencyConflict（同 key 不同内容 → 冲突错误），不是简单吞掉。
multica.task_command_idempotency · task_execution_run_idempotency · group_chat_idempotency
13 返回 + 事件广播
响应体立即返回（Worktree 列表一次返回 human_state / machine_state / ahead / behind / dirty / health_score / risk_count / test_state / locked / archived / version 等字段）。变化通过 SSE / WS 推给订阅方，前端被动更新。
group_api.rs:540-582 响应映射 · crates/api/src/arg/sse_hub.rs · bff/src/collaboration/wss_hub.rs

03 错误码语义 领域错误统一映射

领域 crate 抛自己的错误类型，API 层统一映射成 (code, source, retriable) 三元组。 客户端应该看 code，不要匹配 HTTP 状态做业务分支。

codesourceretriable典型来源客户端应该做什么
POLICY_DENIEDPolicy否PermissionDenied（5 个 domain 共用）停止重试，提示权限不足
SCM_CONFLICTExternal否ScmError::Conflict / IdempotencyConflict提示同 key 内容不一致
SCM_PROVIDER_ERRORExternal是外部 Git Provider 故障可退避重试
WORKTREE_CONFLICTExternal否WorktreeError::Conflict提示 checkout 冲突
VL_CONFLICT / VALIDATION_FAILEDExternal / Validation否validation / search 域修正输入
*_NOT_FOUNDValidation否各域 NotFound（SCM / FB / RESOURCE…）不重试
INTERNALInternal是各域 Internal（6 处统一映射）可重试，但应上报

04 真实 SQL 源码原样

租户注入（第 7 步）

sqlx::query("SELECT set_config('app.tenant_id', $1, true)")
    .bind(tenant_id.to_string())
    .execute(&mut **tx)
    .await
    .map_err(|_| GroupApiError::internal())?;

项目角色绑定复核（第 8 步）

sqlx::query_as::<_, ProjectBinding>(
    r#"
    SELECT id, role, version
    FROM permission.project_role_binding
    WHERE tenant_id = $1
      AND project_id = $2
      AND user_id = $3
      AND valid_from <= now()
      AND valid_to IS NULL
    FOR SHARE
    "#,
)

05 现状与计划 别把 stub 当实装

这一节是本页最重要的诚实标注。middleware/ 下三个中间件在源码注释里明确写着 MVP 阶段 no-op，且尚未组装进 Router：

模块当前状态（源码原文）计划实现内容影响面
middleware/auth.rsno-op stub AuthLayer 未注册 解析 Authorization: Bearer <api_key>、查 api_keys（M 类 / SCD Type 2）、校验 active 状态、bcrypt/Argon2id、签发 scope、IP 白名单、注入 ActorContext API key 直连调用方
middleware/rate_limit.rsno-op stub RateLimitLayer 未注册 60 req/min + 1000 req/hour per key、burst 2× token bucket、429 + Retry-After、MVP in-memory → Phase 2+ Redis 过载保护
middleware/audit.rsno-op stub 未注册 请求级审计（当前审计靠各域的 *_audit 表落库，不是中间件） 审计覆盖面
与之相对，已经实装的是 OAuth2 路径：生产路由 build_group_router 的 handler 使用 AuthenticatedUser extractor + require_scope() + set_tenant() + active_binding()， 这四步都是真实代码。所以"OAuth2 已实装" 与 "API key 中间件未实装" 同时成立，不要混为一谈。
另一个容易误读的命名：rbac.rs 里的 BusinessDomain { player, economy, match, social, admin } 是 RGS 仓的 5 域历史治理命名，不是 Star 的 22 DDD bounded context，也不与 domain-* crate 建立映射。 看权限模型请以 permission.* 表 + ActorContext.roles（5 个合法值）为准。
