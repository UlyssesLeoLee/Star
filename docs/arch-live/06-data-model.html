03 W/T/M 三类横展 硬约束

所有 DB 基本设计阶段必须把表分门别类到三类之一，100% 覆盖，禁止"混在一块列"：

W Work（作业中）

流程中的临时态：session-bound，完成即清理。

物理删除：允许
过期：定时器
retention_period：必填

例：CLI session、heartbeat 之外的临时缓存、排队中的 job

T Transaction（业务事实）

事件流水：append-only，是审计与复盘的依据。

物理删除：禁止
审计：必填
RLS 13 类：必携

例：task_lifecycle_audit、task_execution_run_event、hook_execution_event

M Master（参考 / 设定）

参考数据与慢变配置：变更要走历史版本。

物理删除：禁止
SCD：Type 2
RLS 13 类：必携

例：project_role_binding（valid_from/valid_to 生效期）、quota、profile catalog

混合分类的处理规则：若一张表同时像 M 和 T（典型：带"当前态 + 历史"双表的模式）， 主分类单计，并在"已知缺口"里显式列出待 DDD Review Lead 确认——不允许含糊带过。 其余多分类横展（status / role / permission / policy / event / tag / category…）按同一规则全部独立列举。

04 SCD Type 2 的实际形态

Master 类表不做 UPDATE 覆盖，而是"关掉旧行 + 插入新行"。这就是为什么权限查询长这样：

SELECT id, role, version
FROM permission.project_role_binding
WHERE tenant_id = $1
  AND project_id = $2
  AND user_id = $3
  AND valid_from <= now()      -- 已生效
  AND valid_to IS NULL            -- 未失效 = 当前版本
FOR SHARE

为什么用 valid_to IS NULL 而不是 valid_to > now()

后者需要"未来生效"的记录提前可见，权限就会提前泄漏。用 NULL 表示"尚未失效"， 配合 valid_from ≤ now()，任何时刻的权限集合都是唯一且确定的。 FOR SHARE 再保证读到的行不会在本事务中途被改掉。

回滚为什么也是"新增 revision"

Hook 策略回滚不删记录，而是生成一个新 revision 指回旧内容。 这样"曾经发布过什么"永远可查——对安全策略来说，"能证明某时段用的是哪个版本"和策略本身同等重要。

05 幂等表族 多 Agent 的必需品

多 Agent 并发下，同一个意图被提交两次是常态而不是异常。4 张幂等表覆盖 4 类可重放动作：

表防护对象冲突语义
multica.task_command_idempotencyTask 状态迁移命令同 key 同内容 → 返回首次结果；同 key 不同内容 → 冲突
multica.task_execution_run_idempotency执行运行防止 Agent 重启后重复执行同一轮
multica.group_chat_idempotency聊天消息投递断线重连后重发不产生重复消息
automation.schedule_rule_command_idempotency排程规则变更自动触发与人工触发撞车时不双写
关键区别："同 key 不同内容"必须报冲突，不能静默返回首次结果。 静默吞掉会掩盖真实 bug（调用方参数错了却以为成功了）。ScmError::IdempotencyConflict 就是为此存在。

RLS 的执行前提是会话里已经设好 tenant——这就是请求生命周期第 7 步 必须在事务开头执行 set_config('app.tenant_id', …) 的原因。 漏掉这一步，RLS 不会报错，只会静默地按策略默认值返回空集或全部——这类 bug 极难发现，所以把它放在第一步而不是最后一步。

运维提醒：RLS 策略依赖会话变量，所以直连 psql 查询与走 API 查询的结果可能不同。 排查"API 查不到但表里有数据"时，先确认会话 tenant 是否设置——这是最常见的一类误判。
