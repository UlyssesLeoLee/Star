03 一次动作是怎么被"构造"出来的

整条链路是同一条，不因入口不同而变——这是本仓最重要的结构事实：UI、CLI、MCP 三个入口共用同一套 domain service 与同一张表。

1 / 7
1 触发：三个入口之一 Next.js star-cli star-mcp
同一个业务动作（例：把 Work Item 推进到 review）可以由页面点击、CLI 子命令、或 MCP tool 触发。三者只负责"把意图翻译成协议"，不含业务判断。
frontend/src/app/(app)/.../work-items/ · crates/star-cli/src/commands/task.rs · crates/star-mcp/src/tools/
2 边缘路由：envoy 按前缀分流
5 条前缀规则决定落到哪个进程；带重试策略与熔断阈值；不在白名单的一律 404，不做隐式兜底。
deploy/k3s-local/envoy/configmap.yaml → /api/v1/ /oauth/ /ws/ → star_api_rest · /mcp/ → star_mcp · /actuator/ → star_ops
3 鉴权：OAuth2 + PKCE → AuthUser
校验通过后产出 AuthUser { tenant_id, user_id, scope }；每个 handler 还要再做 require_scope() 与 actor 有效性检查。scope 缺失直接 403。
crates/star-api-rest/src/auth/oauth/{middleware,pkce,keypair}.rs · src/group_api.rs:629 require_scope
4 权限：RLS 前置绑定 tenant
请求进入事务后第一条 SQL 就是 set_config('app.tenant_id', …)，之后所有查询自动被行级安全策略过滤。租户隔离不是应用层约定，是数据库强制的。
crates/star-api-rest/src/group_api.rs:584 set_tenant · db/migrations/*-rls-*.sql（525 条 POLICY）
5 角色绑定：project_role_binding 复核
校验 (tenant, project, user) 是否存在有效绑定（valid_from ≤ now() AND valid_to IS NULL），拿不到即 404。权限 = OAuth scope ∩ 项目绑定 ∩ RLS 策略，三层同时成立。
crates/star-api-rest/src/group_api.rs:596 active_binding · permission.project_role_binding
6 领域服务 + 事务 + outbox
domain-* crate 执行业务规则；写操作在单事务内落"当前态表 + 审计表 + outbox 表"，保证"状态变了但事件丢了"不会发生。
multica.task_lifecycle_current / _audit / task_run_outbox · star-mutex DomainMutex + VersionCAS
7 回流：SSE / WS 推给所有订阅方
响应体立即返回；变化通过 SSE hub 或 WebSocket 广播，Canvas、BI、审计视图被动更新，无需轮询。UI 因此是"事件驱动"而不是"定时刷新"。
crates/api/src/arg/sse_hub.rs · bff/src/collaboration/wss_hub.rs · crates/api/src/chat.rs
为什么这条链重要：它是"多入口一致性"的物理保证。任何绕过第 3–5 步（鉴权 / 权限 / RLS）直接写表的代码，都会同时破坏租户隔离和审计完整性。 守门与 CI 里列了防止这类旁路的规则。
