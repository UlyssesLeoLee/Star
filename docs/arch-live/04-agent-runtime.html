分册 04 · 核心场景

Agent 到底被什么约束住

Agent 不是架构里的"另一条路"，它走的是和 UI 完全相同的 domain service——区别只在于它多了 三道闸：准入 Hook、资源预算、独立验证。这页讲清这三道闸和 10 步闭环。

先说验收底线（仓库硬约束）：任何标为"可用"的 Agent / 任务卡 CLI 功能，必须贯通已授权的 Run/Worktree/Task 绑定 → 实际执行与可控工具调用 → 取消/恢复 → 独立验证 → 有限可审计输出/证据 → 结果回写。 只有 UI、mock、seed、预览适配器或 REST 契约，不得标为可用闭环。缺 provider / sandbox / runtime / 持久化边界时， 应显式禁用执行并说明阻断条件，不能降级为无约束的任意 Shell。

01 十步闭环

1 / 10
1 固定 Run 上下文：profile / digest / 预算
Run 创建时固定 execution profile 的 version 与 digest，并写入快照。执行期间 profile 变化不影响已在跑的 Agent——它用的永远是启动那一刻的快照。这是为了可复现：同一次执行换任何环境都应得到同一结果。
multica.engineering_run_revision · agent_execution_profile · run-profile-snapshot-guards 迁移
2 资源预算预留（quota → reservation → admission lock）
三步递进：先查 Project 级配额，再原子预留额度，最后取 admission lock 防止并发超额。所有预留动作都产生事件（reservation_event）与配额审计。
project_execution_resource_{quota,quota_audit_event,reservation,reservation_event,admission_lock}
3 Spawn fence：阻止重复起同一 profile
同一 Run 内对同一 profile 的并发启动有围栏保护。另有 run-owner 记录，保证一个 Work Item 的执行归属唯一——多 Agent 并发时不会出现"两个 Agent 都以为自己是 owner"。
run-dual-profile-spawn-fence 迁移 · task_run_owner 迁移 · multica.worktree_owner_assignment
4 准入 Hook 判定 安全关键
安全关键 Hook 由 Rust 核心原生执行，fail-closed，不可被插件替代或减弱。判定发生在 BeforeRunAdmission 阶段，结果是 5 选 1：Allow / Deny / RequireHuman / Defer / AllowedByBuiltinBaseline。没有 Allowed 就没有执行。
crates/domain-hook/src/lib.rs · HookPhase / HookDecision · 迁移 multica.hook_execution_event
5 绑定 Task ↔ Worktree（1:1）并建 CLI session
Task 与 Worktree 是 1:1 绑定，不是 1:N。CLI session 建在绑定之上，session 的所有输出都受 Worktree 上下文约束。需要附件时走 attachment ticket 申请限定范围授权，不给万能路径。
multica.work_item_worktree · star-taskgraph · group_api/cli_sessions.rs
6 状态机：7 态推进
任务生命周期是显式状态机，非法迁移直接拒绝：Pending → Claimed → InProgress → PendingReview → Completed，旁路 Failed / Cancelled。每次迁移写 current + audit 两张表。
crates/star-task TaskStatus（7 态）· multica.task_lifecycle_current / _audit
7 受控执行：权限、scope、资源预算三重校验
执行期间的每次工具调用都要过当前权限、策略版本与资源预算校验。Hook 策略在执行中被改动时，按启动时的版本判定——避免"跑到一半规则变了"导致不可解释的结果。
domain-hook POLICY_SCHEMA_VERSION · EVALUATOR_API_VERSION · star-credential（凭证经 KMS 存储，运行时解密）
8 独立验证 不由执行者自己判
执行完成后走独立验证通道，产出结构化证据（task_execution_evidence）与事件（task_execution_run_event）。验证失败不自动重试——重试受 cooldown 约束，防 retry storm。
multica.task_execution_evidence / _event · FailureReason 5 类分类
9 幂等与 outbox：结果可重放
执行运行本身有幂等表（task_execution_run_idempotency），结果通过 outbox（task_run_outbox）投递。重复上报不会造成重复副作用。
multica.task_execution_run_idempotency · task_run_outbox
10 结果回写 + 取消/恢复可用
状态、证据、审计在同一事务落库；SSE 推给 Worktree / Run / Canvas 订阅方。取消是一等操作（有界队列 + drain），恢复从 task_execution_run 的最后事件继续，不从头重跑。
multica.task_lifecycle_* · star-dispatcher（L0 派发）· star-taskqueue（SQLite WAL）

02 状态机与失败分类

TaskStatus · 7 态

Pending → Claimed → InProgress → PendingReview → Completed
旁路出口： Failed · Cancelled

只有 Claimed 能被具体执行者持有。状态迁移必须显式声明，不存在"隐式完成"。

FailureReason · 5 类（可枚举，不是自由文本）

IterationLimit · AgentFallbackMsg · APIInvalidRequest
CodexSemanticInactivity · CodexResumeOversized

把失败原因枚举化，才能做重试策略差异：APIInvalidRequest 重试无意义，IterationLimit 需要降预算重试。

NotFoundType · 4 类（区分 404 语义）

WorkspaceNotFound · TaskNotFound
RuntimeNotFound · Unauthorized

最后一种是鉴权问题却走同一个类型——客户端不能靠 404 推断资源是否存在。

ActorType · 5 类（谁发起的）

Mavis · DomainLead · Subagent · System · Human

执行者身份随记录落库，事后能区分"人点的"与"Agent 自己发起的"。

03 Hook 判定器 Rust 原生 · fail-closed

Hook 是安全关键路径，因此由 Rust 核心原生执行，fail-closed，且不可被插件替代或减弱。 旧的 Python Hook handler 仅能作为显式非权威的兼容/观测输入，不参与授权、命令放行或验收决策。

为什么规则数/条件数/文档大小都要设上限：Hook 在每次执行前都要跑。策略是无上限的话，一次误操作写进去几千条规则， 就会把所有 Agent 启动拖成慢动作。这是可用性风险，不是安全风险——但同样致命。上限让最坏情况可预测。

04 策略继承与快照

Hook 策略是 Project / Worktree 两级：Project 是基线，Worktree 可覆盖。查询"实际生效策略"时必须走解析链， 而不是只读 Project 表——这是 /hook-policy/effective 端点存在的唯一理由。

05 Local Runtime 心跳

Agent 跑在用户机器上的 Local Runtime 里。它不是"后台服务"，而是受约束的本地执行环境，5 条不变量：

不变量内容为什么需要
INV-RT-01LocalRuntime 必须关联 tenant_id本地执行也必须能归属到租户，否则无法审计也无法隔离
INV-RT-02WorktreeMount 必须关联 runtime_id + worktree_id挂载关系可追溯，出问题能定位到哪台机器
INV-RT-03local path 平台不通用（INV-WT-04）跨 OS 假设会导致路径解析错误，必须显式建模
INV-RT-04心跳超时 > 300s → Status = Offline不能等 Agent 自己报告下线；断电/断网也必须能被判定为离线
INV-RT-051 User → N Runtime；1 Runtime → 1 User（owner 唯一）共享 Runtime 会导致责任归属与权限边界模糊
心跳表是 append-only：所有心跳事件都留档，不做覆盖更新。好处是能事后回答"这台机器当时到底在不在线"， 坏处是需要定期归档——这正是 数据模型里 W/T/M 分类要处理的张力。

06 5 角色签字 编译期强制

报告的 5 个签字栏不是流程约定，而是 crates/leads 里的类型：SignOffPanel 聚合 Lead { Architecture, Sre, Platform, Reviewer, Pm }。漏签任何一个，编译不过。

为什么把签字做成类型

流程约定会被绕过（"先发出去，签字回头补"）；类型不会。把 5 角色做成 enum、把签字做成必填字段后， "漏签"从一个流程问题变成一个编译错误。

决策权威抽象

每个 Lead 实现 DecisionAuthority trait，产生 LeadDecision 记录。 决策与签字分离：可以"投反对票但仍然签字"（表示知情并承担），也可以"决策不签字"（表示未决）——两种状态在类型层可区分。
