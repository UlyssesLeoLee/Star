分册 02 · 结构主轴

Project → Branch → Run → Worktree

这一条链是整个产品的结构主轴：左侧导航、REST 路由、数据库表、前端页面全部按它对齐。 理解了这条链，105 个 crate 和 150 张表就有了归属位置——不需要逐个读。

01 四级模型与各自的职责

四个概念的身份不同，这是最容易混淆的地方：

① Project云端跨仓库的归属边界 · 租户内隔离单元
一个长期存在的项目容器。它持有成员（members）、仓库清单与角色绑定。所有 RLS 策略的 project_id 维度都指到这里。Project 本身不"干活"，它定义谁能在哪儿干。
▼
② Branch（云端分支身份）远端git 分支 · 远端身份而非本地 checkout
远端分支的身份，不是本地目录。它是 Project 下的协作线，Run 挂在它身上。注意：分支存在 ≠ 有人在上面写代码。
▼
③ Engineering Run协作工作区canonical workspace · 任务/Canvas/分析的归属
Run 是"协作"的唯一归属地：Work Item、Canvas、Workflow、BI/Benchmark、Plugin App、Agent/Runtime 生命周期都属于某个 Run。Run 固定 profile/version/digest 与资源预算，并持有 Run 快照（供 Hook 判定）。
▼
④ Worktree本地 checkout绑定 Branch 的本地目录 · 一次可运行的工作面
真正落盘、能跑 CLI/Agent 的本地 checkout。选中 Run 内的 Worktree 才打开右侧 App tabs，并把它设为当前焦点与 CLI checkout 目标——焦点只有一个。
选中的含义：Project Worktree Index 可以汇总跨 Branch/Run/Worktree 的状态，但那是只读汇总视图， 不取代 Branch → Run 主导航。一旦用通用任务列表或本地 seed 冒充生产管理，就破坏了这条轴。

04 从导航到数据库：一条路径贯穿四层

这条链解释了为什么 DB schema 里到处是 worktree_id、engineering_run_id、branch_id—— 它们不是冗余外键，而是同一棵树的四级指针。

证据：四级模型的硬约束原文与路由来源
  • 四级主导航是仓库硬约束，见 AGENTS.md §0「产品导航与 Worktree 管理硬约束」：必须以此解决多 Agent Worktree 归属、Branch/checkout 绑定、锁与冲突信号分散等问题。
  • 前端路由树来自 frontend/src/app/**/page.tsx 实扫（57 个），主干链为 (app)/projects/[project_id]/branches/[branch_id]/runs/[engineering_run_id]/worktrees/[worktree_id]/page.tsx。
  • 50 条路由模板来自 crates/star-api-rest/src/group_api/*.rs 的 .route(...) 字面量，已排除测试用 UUID 字面量；数量由 arch_live_doc_check.py 校验（下限 45）。
  • 路由组合入口：crates/star-api-rest/src/group_api.rs:656 build_group_router，merge 13 个路由组 + 1 条内联 group-context。
  • Hook 策略的 10 条路由挂在 Project 与 Worktree 两个层级（hook_policies.rs），既支持继承也支持 Worktree 覆盖。
