分册 08 · 约束系统

哪些规则会真的拦住你

分三层：编译器强制（workspace lint，绕不过）、CI 强制（红就合不进去）、 流程约定（AGENTS 守门，靠自觉）。分清这三层，才知道"我能不能先合了再说"。

01 编译器层 不可绕过

这 4 条写在 workspace 根 Cargo.toml 的 [workspace.lints.rust]， 任何 crate 写 [lints] workspace = true 后自动继承，编译不过就是编译不过。

lint级别拦什么代价
unsafe_codeforbid任何 unsafe 块连 unsafe fn 都不行（forbid 比 deny 更严，不能用 #[allow] 解除）
missing_docsdeny公开项缺文档注释从 warn 升到 deny 是刻意选择：公共 crate 的 API 应当自解释
unreachable_pubdenycrate 外无法访问却标 pub 的项防止"看起来是公共 API 其实没人能用"，是 crate 边界卫生
rust_2018_idiomsdeny2018 之后遗留写法纯现代化，无行为变化
这 4 条的价值在于"无讨论空间"。安全相关的规则最怕"这次赶时间先放开"。写成编译器 lint 之后， 放宽它需要改根 Cargo.toml 并留下 commit 记录——而不是靠一句"我本地能跑"。

04 门禁本身会骗人 四个真实陷阱

这四条不是理论，是本仓在加固过程中实际踩到并修掉的。写新门禁前请先读完这节。

① 报绿 ≠ 跑过

某次 CI 4/4 全绿，但读日志发现 semgrep 门禁一次都没真跑过：前序 step 失败导致后续 step 被整体跳过， 而它用的第三方 action 在工具崩溃时没有让 step 失败。

怎么判：先看该 job 实际执行过哪些 step（被跳过的根本不会出现）， 再看工具自己的结论行（如 Ran 725 rules on 358 files: 0 findings）。不要只看 job 的 success/failure。

② 文本解析门禁的 0 = 未知

某命名门禁的表解析器漏了一种建表写法，从 39 个列名里静默抽出 0 个， 报告输出与"仓库完全干净"完全无法区分。

修法：解析结果为 0 必须 fail-closed； 每个集合配一个人工核对过的数量下限；并且必须做变异测试——注入违规看它变红、 不注入的对照组仍绿，两者缺一就无法区分"门禁有牙"和"门禁没跑"。

③ 加严配置自身引入回归

给脚本加 set -euo pipefail 后，原本正常的 git log | head -30 || echo "N/A" 变成在真实日志后多打一个 N/A （head 先退出 → git log 收 SIGPIPE 非零 → pipefail 冒泡）。

做法：给长期能跑的配置加严格开关时， 逐个审视 || / && 兜底分支会不会被新语义误触发；安全类改动收尾必须自审 diff， 重点看"我为了让代码更严而加的那些东西"。

④ 修复会悄悄磨掉已有断言的牙

本站点修「无 JS 时数字全显示 0」时，把 data-count 的初始文本改成真实值（改对了）。但这同时让 textContent === data-count 这条断言在一个 JS 都没跑的页面上也成立。 几小时后 arch.js 出了语法错误、整站交互全失效，而这条数字断言依然全绿。

规律：只比较"最终状态"的断言， 原理上区分不了"跑完了且正确"和"一行都没跑"；而"把初始态改成等于终态"这种常见健壮性修复， 恰好抹掉唯一能作证的差异。做法：凡是靠 JS 产生最终态的断言，开头第一句先验 html.anim（由 boot() 添加）在不在，让"没跑"以可读字符串报出来； 往返类用例要在中途取快照并断言中途确实翻转过。
附带：在 /* */ 注释里原样引用一个正则，其中的星号斜杠序列会当场结束注释， 后面整段中文被当成 JS 解析 → 整份脚本 SyntaxError。这类错 node --check 一秒能判， 所以 arch_live_doc_check.py 把静态语法校验放在所有门禁最前面。

05 这套文档自己的门禁

本套文档不是"写完就算数"。它带三个脚本，分别防内容漂移、交互失效、渲染失效：

drift arch_live_doc_check.py

重新扫描仓库，把真实值与页面里 data-fact 声明的值逐条比对， 并核对 data-count 的初始文本（无 JS 时就显示这个值）。 运行前先 node --check 共享脚本，语法错直接 exit 1。

python scripts/automation/arch_live_doc_check.py
python scripts/automation/arch_live_doc_check.py --self-test

退出码：0 一致 / 1 漂移或资产语法错 / 2 无法解析（不等于"干净"）/ 3 路径缺失。 另有 --sync-seed 与 --rebase-baseline 两个修复入口。

interact arch_live_interact_check.py

用 Playwright 真点按钮并断言 DOM，覆盖 9 页共 28 项： 步进器往返/钳位/自动播放、标签页、crate 过滤联动、主题切换， 以及无 JS 与 prefers-reduced-motion 两条降级路径。

python scripts/automation/arch_live_interact_check.py
python scripts/automation/arch_live_interact_check.py --mutate

--mutate 把已知 bug 注入站点副本， 要求对应用例必须变红且对照组全绿——没跑过红的门禁只是装饰。实跑 8/8 变异被抓到。

render arch_live_shot.py

用仓库自带的 Playwright 对 9 个页面各生成一张整页 PNG，落到 .preview/ （已 .gitignore，可随时重建）。用来确认"页面真的渲染出来了"，而不是"HTML 写完了"。

python scripts/automation/arch_live_shot.py
python scripts/automation/arch_live_shot.py --pages index.html

同样 fail-closed：页面数为 0、产物缺失或过小都 exit 2。

为什么文档也要有门禁：本仓最容易发生的失败模式不是"没写文档"，而是文档比实现旧—— 架构文档写着某能力已实装，代码里还是骨架。上面的 no-op stub 标注就是靠这种对照才能发现。 数字能被机器核对的部分就交给机器；不能核对的（"已实装/仅骨架"）就在页面上显式标注证据路径。
本套文档自己也踩了这条：第 05 节长期写着"它带两个脚本"，而实际已经有三个—— 截图能证明"渲染出来了"，但证明不了"点得动"，所以必须再有第三个脚本。 补上之后它又跑出 4 个 bug（README bug 表里的 ①②④⑤；第 ③ 条种子值是读代码时发现的， 不是门禁抓的——这恰好说明机器能覆盖和只能靠人读的部分要分开记账）。
