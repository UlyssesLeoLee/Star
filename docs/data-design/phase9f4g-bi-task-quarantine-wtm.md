# Phase 9F4G BI Task Quarantine — W/T/M Design

## Scope and classification

`bi.task_event_quarantine` is owned by the BI persistence boundary and is classified as **T — Transaction**. The design adds no Work queue and no Master configuration table. For the BI Task-event tables after this slice, W/T/M coverage is 0/4/0: Inbox receipt, projected event fact, integrity incident, and quarantine receipt are all durable business/audit facts.

| Column group | Columns | Classification and invariant |
|---|---|---|
| Tenant and receipt identity | `tenant_id`, `quarantine_id`, `consumer_id`, `recorded_at` | T. Tenant scopes access; receipt ID is generated by PostgreSQL; consumer identity is fixed to the BI Task-event consumer; timestamp is server-generated. |
| Sender and transport route | `sender_service_id`, `receiver_service_id`, `transport_provider_id`, `transport_provider_version`, `transport_profile_id`, `transport_profile_revision`, `transport_profile_digest`, `endpoint_identity`, `destination_id`, `destination_generation` | T. Captures the immutable route asserted by the trusted Rust adapter. The schema validates formats and binds the values into the unique cursor key; this database function does not prove them against an authoritative route-pin registry. |
| Source cursor | `origin_provider_identity`, `source_log_id`, `source_log_generation`, `source_sequence` | T. Together with the full route, identifies the source position for idempotent terminal-fault handling. Provider identity must equal the pinned transport provider. |
| Immutable event evidence | `message_id`, `wire_sha256`, `wire_length`, `fault_code` | T. Message identity, exact-wire digest and length are compared on replay; fault is an allowlisted enum. No event bytes, payload, arbitrary headers or free-form error text are stored. |

## Keys and replay behavior

- Primary key: `(tenant_id, quarantine_id)`.
- Unique idempotency key: tenant + consumer + sender/receiver + provider/version + profile/revision/digest + endpoint/destination generation + source provider/log generation/log/sequence.
- Exact replay returns the original receipt only when message ID, wire digest, wire length and fault code all match.
- A changed value under the same key returns `conflict` with no receipt and leaves the original row untouched.
- The fixed owner function inserts at most one row per cursor; PostgreSQL uniqueness serializes concurrent attempts. Two-session exact and conflicting-content races are covered by the disposable runner.

## Retention, isolation, and privileges

| Concern | Design |
|---|---|
| Lifecycle | Permanent append-only Transaction evidence in this slice; there is no TTL, purge worker or ad hoc deletion path. A production retention/privacy policy remains open and ingestion stays disabled until approved. |
| RLS | Tenant `FORCE ROW LEVEL SECURITY`; owner policy reads transaction-local `app.tenant_id`. Missing or mismatched tenant context is rejected. This GUC is a call-scope constraint, not authentication against a compromised runtime able to set the value. |
| Runtime access | For this quarantine table, runtime has no direct table privileges; this migration grants `EXECUTE` on the fixed `SECURITY DEFINER` writer and revokes `PUBLIC EXECUTE`. The fixture verifies NOINHERIT and rejects membership that permits runtime `SET ROLE` to the owner; target role configuration remains a deployment gate. Function owner is a non-login, non-superuser, non-BYPASSRLS role with fixed `search_path=pg_catalog` and `row_security=on`. |
| Immutability | `UPDATE`, `DELETE`, and `TRUNCATE` are rejected by the append-only trigger, including when invoked by the table owner. |
| Payload privacy | Table schema contains no wire/payload or free-form error columns. Only bounded route/cursor identifiers, a digest, exact length, message ID, fixed fault code and server timestamp are persisted. |
| Production trust | A trusted Rust adapter must authenticate the transport and resolve/verify the immutable route before calling the function. The database only validates supplied metadata and scope. Production identity, route registry, target DB grants/RLS deployment, crash recovery, backup/WAL and retention approval remain release gates. |

## Verification boundary

`scripts/automation/phase9f4e_bi_task_event_inbox.py` applies the migration twice to an isolated loopback PostgreSQL 18 instance and runs schema/privilege/RLS/WORM/input/replay/conflict assertions plus deterministic independent-session unique-key lock-wait races. Same-cursor conflicting attempts return no receipt and do not create a second incident record. The append-only table has no quota, partition or production retention policy. Passing this fixture does not prove target database deployment, production identity, crash/PITR behavior, Rust compilation or production ingestion readiness.
