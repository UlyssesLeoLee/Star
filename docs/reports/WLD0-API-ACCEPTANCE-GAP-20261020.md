# WLD-0 Run-to-Worktree API Acceptance Gap

## §0 Purpose and scope

This is a bounded, read-only review of the Run-to-Worktree binding API at the assigned `dev` baseline `6e3e31ce34ae7eb6d6ee1de7066f693de48c172e`. It covers bind, reassign and detach authorization, optimistic concurrency, SCD2 history, idempotency, audit and Outbox writes, SQL error behavior, and currently available tests. No product code, migration, test, or database was changed or executed. This report complements `docs/reports/WLD0-TARGET-DB-AUDIT-20261020.md`; neither report closes WLD-0 target-database acceptance.

- The only PostgreSQL test in this module is ignored unless `STAR_WLD0_BINDING_TEST_DATABASE_URL` is explicitly set. It verifies advisory-lock exclusion for one Worktree and independence for another; it does not call the API or mutate bindings (`:1161-1217`).
- The route integration test uses `connect_lazy` to an unavailable database and exercises only missing authentication (`crates/star-api-rest/tests/engineering_run_worktree_binding_routes.rs:29-68`). It is not PostgreSQL acceptance.
- The earlier WLD-0 report documents a disposable schema-only run for migrations through 2026-10-01; it did not apply 2026-10-15/19, use the application role, or exercise binding writes (`docs/reports/WLD0-TARGET-DB-AUDIT-20261020.md:18,22-25`).

## §4 Open gaps and decisions

1. No source evidence supplies the actual API DB login/group role or the least-privilege grants required by this handler and its triggers. WLD-0 needs the intended role contract and effective-grant evidence before RLS can be accepted.
2. No database-backed authenticated API test currently covers the lifecycle. The ignored lock test is not a substitute for CAS or end-to-end persistence tests.
3. Exact replay after Run-grant revocation is designed to re-authorize the target Run before returning the stored response, but this behavior is untested. The conflict-replay path returns the key-reuse conflict before checking the target Run; verify the no-leak behavior is acceptable.
4. Reassign currently emits one Outbox event under the target Run and carries the previous Run in payload. Confirm whether the former Run's BI/subscribers require a separate departure event or whether the target-scoped event is the intended contract.
5. Trigger-raised invariant failures that are not SQLSTATE `23505`, `23503`, or `23514` map to generic internal error; decide whether this is the intended API response for guard failures and assert it in integration coverage.
6. The 2026-10-15 host-independent migration is not safe for blind replay after successful application according to `docs/reports/WLD0-TARGET-DB-AUDIT-20261020.md:17,30-35`; the replay/rollback protocol is a separate prerequisite for the matrix.
7. There is no selected-Worktree focus version in this binding API. If focus selection is expected to be part of mutation concurrency, its owner and CAS contract must be specified separately; this API only guards the Project relation and Run binding versions.

## §5 Guardrails

- Treat this as a source acceptance-gap audit, not implementation or target-deployment acceptance.
- Separate unit tests, lazy-pool route tests, disposable-schema tests and target-role RLS tests; do not use one evidence tier as another.
- Use only an identity-confirmed disposable DB for mutation, rollback, replay, duplicate-row and concurrency tests.
- Verify the real restricted application role, effective membership and grants; a migration owner, superuser or `BYPASSRLS` role cannot prove RLS acceptance.
- Preserve execution admission as closed. The response and Outbox payload explicitly state it is unavailable (`run_worktree_bindings.rs:886,919-933`).
- Update WLD-0 requirements/design and WBS acceptance state only after the implementation and target-appropriate evidence are complete.
